## 10. P1: реклама и бизнес с несколькими магазинами

- [ ] Проверить определения показов, кликов, заказов, атрибутированной выручки, расходов и периода атрибуции.
- [ ] Не смешивать рекламную атрибуцию с фактической датой продажи в общих метриках.
- [ ] Проверить производные показатели при нулевых показах, кликах, заказах и выручке.
- [ ] Добавить fixtures бизнеса с двумя магазинами, одинаковыми SKU и неполной детализацией отчёта.

**Критерий приёмки:** рекламные расходы не теряются и не удваиваются; область данных видна в интерфейсе; недоступная атрибуция по магазину явно обозначена.

## 15. Обязательная матрица тестов

Использовать существующие тестовые наборы и команды репозитория. Интеграционные тесты, миграции и ремонт данных выполнять только в изолированной тестовой БД.

| Уровень | Обязательные проверки |
| --- | --- |
| Unit | Идентификаторы, финансовые категории, даты/суммы, цены, ставки, остатки, неизвестные значения |
| Worker | Watermark, окна отчётов, retries, локи, первый запуск, backfill, частичный сбой |
| API | Строковый SKU биддера, валидация ставок, права, фильтры, capability-состояния, backfill рекламы |
| ClickHouse | Raw → stg → mart, дедупликация, повторный rebuild, исторический возврат, ремонт финансов |
| UI/E2E | Переключение площадки/аккаунта, создание правила, ошибки, неполные данные, отправка остатков |
| Регрессия | Существующие WB/Ozon сценарии и общие финансовые определения |
| Реальный кабинет | Чтение, сверка отчётов, отдельно разрешённые изменения и проверка результата |

- [ ] Добавить обезличенные fixtures на основе фактических форматов API, не содержащие ключи и персональные данные покупателей.
- [ ] Убедиться, что тесты не проверяют только заранее нормализованные строки, обходя проблемный парсер.
- [ ] Проверить нулевые данные, неизвестные поля/операции и отсутствие необязательных полей.
- [ ] Запустить целевые unit, worker, API и ClickHouse integration тесты.
- [ ] Запустить общие регрессионные тесты, линтеры, проверку типов и сборку frontend согласно конфигурации репозитория.
- [ ] Сохранить команды, результаты и перечень реально выполненных/пропущенных проверок в отчёте реализации.

## 18. Definition of Done

- [ ] Все P0 и P1 выполнены либо для недоступной по API возможности отдельно согласовано и документировано ограничение. Нерешённый баг не считается ограничением API.
- [ ] Строковые SKU YM проходят полный путь создания и исполнения правила биддера.
- [ ] Название товара не влияет на финансовую категорию; контрольные суммы сверены.
- [ ] Пропуски после простоя восстанавливаются; backfill и повторные загрузки идемпотентны.
- [ ] Исторические продажи и возвраты восстановлены в пределах доступных источников; неполнота явно отражена.
- [ ] Общие финансовые показатели сопоставимы между YM, WB и Ozon.
- [ ] Остатки отправляются только в заявленный и поддерживаемый адресат.
- [ ] Многомагазинная реклама не теряется и не дублируется; бизнес- и магазинные данные не смешиваются.
- [ ] Цены, репрайсер, отзывы, каталог, воронка и интерфейс прошли заявленные сценарии.
- [ ] Права, изоляция организаций, маскирование секретов и запрет внешних действий проверены.
- [ ] Целевые и регрессионные тесты пройдены; пропущенные проверки не обозначены успешными.
- [ ] Уже загруженная история исправлена или перечень невосстановимых данных зафиксирован.
- [ ] Реальная сверка выполнена; отсутствие разрешения на тестовые записи отражено как незавершённая проверка, а не как подтверждённая готовность записи.
- [ ] Итоговая матрица паритета содержит ссылки на тесты и результаты проверки каждого контура.

Только после выполнения этих условий поддержку можно обозначать как полную в заявленной области. Наличие `ym` в фильтрах и отдельных адаптеров само по себе таким подтверждением не является.
