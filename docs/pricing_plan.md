- **Попутно:** время в `sys_task_runs` писалось со сдвигом на UTC-офсет сервера (на проде −2 ч).

Что выяснилось на реальных данных:

- **Скидка маркетплейса.** У WB её нет в API цен, у Ozon метод `/v1/product/prices/details` закрыт (403, вероятно Premium), а `v4/product/info/prices` удалён. Поэтому скидку измеряем по фактическим продажам:
  - WB: `finishedPrice / priceWithDisc` в заказах;
  - Ozon: `sale_price / seller_price` в начислениях, где `seller_price = sale_price + bonus + coinvestment`.
- **СПП WB у заказчика** по товарам 21–38% (медиана по кабинету ~23,5%). Это совпадает с её «37%».
- **Ozon доплачивает ~50–60%** цены продавца. Режим «держать цену для покупателя» поднимал бы цену на Ozon почти вдвое, поэтому `max_price` и шаг обязательны.
- **Мало продаж для замера скидки.** Только у 10 из 296 карточек WB и ~80 из 270 Ozon хватает продаж (≥ 3) для замера скидки по товару. Решено (2026-10-17): на WB репрайсер работает и по медиане СПП по кабинету (от 10 заказов); на Ozon только по замеру на товаре.
- **Цены на WB и Ozon расходятся сильно:** у части наборов цена для покупателя на WB в 2–2,5 раза выше, чем на Ozon.

## Этап 2. Таблица «Разбор цены» (только чтение, первая видимая польза)

- `GET /api/v1/pricing/breakdown?marketplace=…`
- Формулы для WB:
  - Зачёркнутая = `price`.
  - Цена со скидкой = `price × (1 − discount)`.
  - Цена для покупателя = цена со скидкой × `(1 − СПП)`.
  - Комиссия = % от цены со скидкой + логистика.
  - Маржа ₽ = цена со скидкой − комиссия − логистика − себестоимость.
  - Маржа % = маржа ₽ / цена со скидкой.
- Для Ozon аналогично, через `old_price` / `price` / `marketing_price`.
- Страница `Pricing.jsx`:
  - Колонки точно как в эскизе заказчика, вкладки по МП.
  - Подсветка, если цена для покупателя ≠ желаемой, и при отрицательной марже.
  - Желаемую цену можно править прямо в ячейке.
  - Выгрузка в XLSX через существующие export jobs.
  - Скидку МП, которую мы вычислили сами, а не получили из API, помечаем как «оценка».

## Этап 5. «Удержание цены»

- **Расчёт цены**, новая логика в репрайсере. Режим «держать цену для покупателя»:
  - Требуемая цена со скидкой = `target / (1 − скидка МП)`.
  - Для WB она пересчитывается в пару `price` / `discount`: скидку продавца сохраняем, меняем `price`.
  - Затем ограничение коридором `[min_price, max_price]` и проверка, что маржа не меньше порога.
  - Режим «держать цену продавца» просто возвращает `target`, если текущая цена с ним расходится.
- **Запись:**
  - WB: передавать `price` и `discount`.
  - Ozon: передавать настоящий `old_price` (исправить баг с `"0"`). Опционально `auto_action_enabled=DISABLED`, `price_strategy_enabled=DISABLED`, `min_price`, чтобы Ozon сам не опускал цену.
  - ЯМ: новый метод.
- **Защита:**
  - dry-run по умолчанию для новых правил.
  - Порог нечувствительности, например ±1% или ±10 ₽.
  - Не больше одной правки товара за окно.
  - Глобальный лимит действий за прогон (уже есть).
  - Kill switch.
- **Уведомления:**
  - Telegram-событие «МП изменил цену товара X: было / стало / вернули».
  - Факт изменения брать из diff в history store, его уже умеем строить.
- **UI:** включение «держать цену» в строке таблицы разбора, журнал действий (уже есть в `Repricer.jsx`, расширить).
