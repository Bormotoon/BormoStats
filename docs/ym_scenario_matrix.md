## 8. Детализированные статусы и ограничения

### 8.1. Финансы (требует исправления)

- **Проблема:** `collectors/ym/parsers.py:309-316` формирует `service_type` из `transactionSource` + `serviceType`, но классификация в `common/finance.py:49-64` ищет по тексту. Название товара (`product_name`) в классификацию не входит — это правильно.
- **Ограничение:** точная категория операций зависит от текста ответа API. Подтверждено: `Платеж покупателя` → `sales`, `Возврат платежа покупателя` → `returns`.
- **Поведение API:** отчёт «Единый финансовый отчёт» возвращает CSV/JSON с полями `TRANSACTION_TYPE`, `SERVICE_TYPE`, `TRANSACTION_SOURCE`, `OFFER_OR_SERVICE_NAME`.
- **Статус:** реализован, требует сверки с реальным кабинетом.

### 8.2. Восстановление исторических продаж (требует исправления)

- **Проблема:** `workers/app/tasks/ym_collect.py` при первом импорте заказа, уже вернувшегося, не восстанавливает дату и стоимость исходной доставки.
- **Ограничение:** API не предоставляет историю изменений статусов в текущем снимке. Доступны только `creationDate` и `statusUpdateDate`.
- **Поведение API:** `GET /v2/orders` возвращает текущий статус заказа без истории переходов.
- **Статус:** требует исправления.

### 8.3. Реклама (business-wide)

- **Ограничение:** отчёт `shows-boost` имеет business-wide область. При нескольких магазинах сбор запрещён.
- **Поведение API:** `GET /v2/businesses/{business_id}/stats/overview` не детализирует по магазинам.
- **Статус:** ограничен источником.

### 8.4. Watermark и backfill

- **Ограничение:** в `ym_collect.py:99-100` watermark продвигается до `now` после успешной вставки. При сбое между вставкой и обновлением watermark данные могут быть загружены повторно.
- **Поведение API:** отчёты генерируются асинхронно; время готовности отчёта зависит от объёма данных.
- **Статус:** реализован, требует проверки идемпотентности.

### 8.5. Модели работы магазинов

| Модель | Статус | Комментарий |
| --- | --- | --- |
| FBY | требует исправления | `grouped` режим остатков |
| FBS | требует исправления | `partner` режим остатков |
| DBS | требует исправления | нет подтверждения |
| Express | требует исправления | нет подтверждения |

**Подтверждение:** проверка одного магазина не доказывает поддержку всех моделей. Требуется проверка каждого режима отдельно.

## 9. Критерии готовности

### 9.1. Готовность кода
- Код написан, проходит линтинг и типизацию
- Unit-тесты покрывают ключевые сценарии
- Интеграционные тесты проходят в изолированной БД

### 9.2. Локальные интеграционные тесты
- Тесты на fixtures с реальными форматами API
